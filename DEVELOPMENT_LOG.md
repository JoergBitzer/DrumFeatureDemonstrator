## How to go back to a state
- Every work package (WP) is a branch `feature/...` that is merged into `main` with `--no-ff` (a merge commit marks the state).
- Every merged state has a tag `state-W<n>-<version>` (not `v*`, so no release workflow starts). `git checkout state-W3-0.2.0` shows the state after W3.
- Nothing is pushed to the public remote during this phase; push (branches and tags) when the author says so.
- Builds use at most half of the cores. Debug build + unit tests + pluginval before every commit; the Release build is installed
  to `~/.vst3/` at the marked points (the rule of `CLAUDE.md`).

### W7: state, sample storage, factory presets, manual (branch `feature/presets-state`, version 0.5.0)
- Sample storage (decision of the plan, extended): the sample is copied into `<user presets folder>/Samples/` (`src/SampleStore.*`; same name + same content = reused, same name + other content = `name_2.wav`), and the name is a property `SampleFile` of the plugin state. Therefore a **preset** carries the sample name (small files), and a **DAW project** carries the sample itself (base64 of the file, up to 8 MB, as a child `SampleData` of the state written by `getStateInformation` only, never into presets); `setStateInformation` writes the file back if it is missing. A change of `SampleFile` (also by `replaceState`, which redirects the tree: `valueTreeRedirected`) loads the sample asynchronously on the message thread; a preset without a sample keeps the current one (its name is written back into the state); a missing file shows "Missing: name".
- Result (Tester `--save-state` / `--load-state`, new): a state saved after loading a MusicRadar cymbal and a pattern, restored in a **fresh home folder** (empty samples folder), gives a bit-identical render (`cmp`), and the sample file is re-created in the samples folder.

### Review fix (branch `fix/sound-start-capacity`, version 0.5.1)
- Own code review of the audio path found one real-time risk: `scheduleBlock` could push more sound starts than the reserved capacity (32) for a very long block (offline render with a huge block size, 8 steps at a fast tempo), which would allocate in the audio thread. Now `kMaxSoundStartsPerBlock = 256` is reserved and `scheduleBlock` stops there; a unit test checks that a ten-minute block neither exceeds the limit nor reallocates.
- Known minor points, not changed: `m_sampleName` / `m_loadedSampleFileName` (juce::String) are written on the message thread and read by `getStateInformation` which a host may call from another thread (a torn read is theoretically possible; the strings are short and change only on load). The GUI notices a changed sample by comparing pointers on a 30 Hz timer.

### Drop of a sample (branch `fix/sample-drop`, version 0.5.2)
- Investigation: the Tester got `--drop <file> [--drop-at x,y]`, which hands a drag-and-drop to the editor's window peer exactly as JUCE's X11 code does after an XDND drop (`handleDragMove`, `handleDragDrop`). Result: the waveform and the grid accept the drop, the sample is loaded, and a second drop **replaces** the first (name and waveform change) -- so the plug-in logic is not the problem. JUCE's X11 code answers every XDND position message with "accept" and only decides at the drop, so a "refusal" cannot come from our `isInterestedInFileDrag`. What cannot be tested here: the real XDND transfer from a file manager or from Bitwig to the plug-in window (host- and platform-dependent; a drag from inside Bitwig's own browser is not an XDND drag at all).
- Changes anyway, to remove every plug-in-side reason for a refusal and to make a failure visible: the waveform and the GUI accept **any** file (the loader decides), the waveform also accepts a dropped **text** (path or file:// address, which some file managers send), and an unreadable file now shows "Could not read X (use wav, aiff, flac or ogg)" in the sample label (before, the message was overwritten after a moment).
- To find out what really happens in Bitwig: does the waveform light up orange while the file is dragged over it? If yes, the drop arrives and the message in the sample label tells why it failed; if no, the host does not pass the drag to the plug-in window (then the Load button is the way).

### Pitch as a note (branch `feature/step-notes`, version 0.6.0)
- The per-step pitch (+-24 semitones relative to the base note) is replaced by a **MIDI note** per step (`Step01Note` ... `Step32Note`, 12 - 108 = C0 - C8, default 60 = C4). The **base note** is where the sample sits in the scale: the playback speed of a step is 2^((step note - base note)/12). Changing the base note therefore transposes all steps and the keyboard together. The step **velocity** is now a MIDI velocity 1 - 127 (default 100, gain = velocity / 127), like the velocity of a MIDI note; its name stays "velocity".
- Code: `StepSettings::noteNumber` (was `pitchSemitones`), `Pattern::baseNote`, `stepSemitones()`, `src/NoteNames.h` (note names, "C4" = 60). Factory presets regenerated (preset version 2). The old parameter ids (`...Pitch`) are gone: presets and DAW projects of 0.5.x lose their per-step pitches (they were not in use outside the tests).
- Verified: unit tests for the base-note relation and the note names; a Tester render with base note 48: step 1 (note 60) sounds an octave up (1998 Hz for a 1 kHz sample, expected 2000), step 5 (note 72, velocity 64) two octaves up with peak 0.252 (expected 0.252).

### Info line, selected step, MIDI step entry (branch `feature/step-cursor`, version 0.7.0)
- **Info line** (a label below the grid): hovering over a step button, mode button or knob, and changing it, shows e.g. "Step 5 note: E4 (MIDI note 64)", "Step 5 velocity: 100", "Step 5 mode: reverse and play to end ...". The knobs stay without edit fields; the second knob is called **velocity** everywhere (tooltip, info line, manual).
- **Selected step:** a click into a step column or the cursor keys (left/right +-1, up/down +-16, Home/End) select a step. While the transport stands (host stopped, or internal beat paused) the selected step has the yellow frame; while it plays the frame follows the playing step. The editor forwards the keys it receives to the GUI (`addKeyListener`), so they work whichever child has the focus (not if the host keeps the keys for itself).
- **MIDI step entry:** a note-on that arrives while the transport stands (also from the on-screen keyboard) is put by the audio thread into a small lock-free FIFO; the GUI timer applies it to the selected step: note, velocity, and the step is switched on (with parameter gestures: undo/automation/red Save button). The sample is also heard. Notes that arrived while no editor was open are discarded when an editor opens. The selection does not advance by itself (decision: cursor keys do that; an auto-advance option is easy to add).
- Checked with the Tester (new `--keys left,right,...` sends keys through the window peer): a note 67 (G4) with velocity 90 while stopped -> step 1 on, note G4, velocity 90, info "Step 1 set by MIDI: note G4, velocity 90"; `--keys right,right,right,down` moves the frame to step 4 (down wraps in a 16 step pattern). Not tested: real mouse hover/click and the real keyboard in a host.

### Drop of files in Bitwig: cause found and fixed (branch `fix/xdnd-proxy`, version 0.9.1)
- The author's observation (Thunar: the dragged file symbol and the drop zone never change) pointed at the host. With Bitwig running, the window tree was inspected (`xwininfo -root -tree`, `xprop`): Bitwig's plug-in host process creates a **top-level window** ("DrumFeatureDemonstrator / DrumFeatureDemonstrator", with `WM_STATE`, transient for the main window) and our JUCE window is a **child** of it (it has `XdndAware`, the host's window has not). A GTK file manager offers a drop only to the top-level window under the mouse (the one with `WM_STATE`), and that window is not drop-aware, so the drag is refused and never reaches the plug-in. That is why the earlier tests in the Tester (which hand the drop to our window directly) worked and the real drag did not.
- Remedy from the X11 drag-and-drop protocol: the property `XdndProxy` on the top-level window names a window that receives the drag messages instead (and that window carries `XdndProxy` pointing to itself). New: `src/platform/XdndProxy.*` (plain Xlib, linked with X11 on Linux) sets it from the editor (a GUI timer tries once a second for up to 20 s until the editor has its host window), does nothing if our window is itself a top-level window (Standalone), never replaces a proxy of somebody else, removes it again when the editor closes, and ignores X errors for windows that disappear. `tests/manual/xdnd_proxy_tool.cpp` applies the same to a given window id.
- The property was also set by hand on the author's **running** plug-in window (`0x6600000` -> `0x6800009`) with that tool, so the drag could be tried without rebuilding (it vanishes with the window). Result of the author's try: see the next entry.
- Checked here: builds without warnings, unit tests pass, pluginval Debug (skip GUI) 3/3, Tester snapshot unaffected (the offscreen window is not embedded). Not testable here: the real drag from Thunar (needs a person).

### Drop still fails in Bitwig with 0.9.1 (branch `fix/xdnd-diagnosis`)
- With the plug-in open in Bitwig the window tree showed that the proxy property **was** set (host window `0x5c00000` -> editor window `0x5e00009`, the editor points to itself). So the first remedy is in place, but the real drag still does nothing.
- Reproduction without a person, three small manual tools (in `tests/manual/`, not built by CMake): `xdnd_source_tool.cpp` plays a drag source by hand, `gtk_drag_source.py` is a real GTK3 drag source (uri list, like Thunar), `xtest_drag.cpp` moves the mouse pointer with XTest (it takes the pointer for about three seconds).
  - Source by hand (version 3 of the protocol, JUCE's) onto the Bitwig window: **works** (target answers, takes the drop, the sample was copied into the samples folder and shows in the plug-in). Note: JUCE announces XDND version **3** (`XdndAware` value 3, xprop shows it as "ARC"); a source must use the lower of both versions.
  - Real GTK source dragged onto the **Standalone** (a top-level window): **works** (Cymbal02.wav loaded).
  - Real GTK source dragged onto the plug-in window **inside Bitwig**: the source's data is requested twice, **but no sample is loaded**.
- To see what arrives in the plug-in, an opt-in log was added (`src/DebugLog.h`): if the file `/tmp/dfd_debug.flag` exists, the drop callbacks, the file lists and the proxy installation are written to `/tmp/dfd_debug.log`. (A Debug build with this log is installed for the author's try.)
- **Result of the author's try (Debug build with the log):** no drop callback at all in the log (only "xdnd proxy installed"), so nothing reached JUCE. Reproduced with the GTK source on the live Bitwig window; with `GDK`'s destination window printed (`context.get_dest_window()`) GTK **does** choose our proxy window, but then sends only one position message and the drag ends with NO_TARGET.
- **Root cause (found with a sniffer, `tests/manual/xdnd_sniffer_tool.cpp`, which became the proxy and printed every message):** a source that uses a proxy sends the messages to the proxy window, but the `window` field of every message still names the **real target window = the host's top-level window**, and it expects the answers (`XdndStatus`, `XdndFinished`) to name that same window in `data.l[0]`. JUCE looks up its peer by the `window` field: it does not know the host window and ignores the messages. So **JUCE's own drop code can never work behind a proxy.** (An earlier "success" with my hand-made source was possible because that tool addressed JUCE's window directly.)
- **Fix (version 0.9.2):** `src/platform/XdndTarget.*` replaces `XdndProxy.*`: the plug-in creates its own invisible window on a second X connection, makes it the proxy of the host's top-level window and is the drop target itself (a small thread: XdndEnter / Position / Leave / Drop, answers with the host window in `l[0]`, takes `text/uri-list`, `XdndFinished`). The first dropped file is handed to the GUI through `MessageManager::callAsync`; the GUI loads it like any other. It waits up to 20 s for the host to attach the editor, does nothing in the Standalone (a top-level window gets JUCE's own drops), never replaces another proxy, and takes the proxy away when the editor closes. `tests/manual/xdnd_target_tool.cpp` runs the class on any window id.
- **Verified here with a real GTK drag source (python GTK 3.24 + XTest) onto the author's live Bitwig plug-in window:** the class reports `DROPPED: file:///.../Cymbal03.wav`, GTK's drag ends without "drag-failed". Not yet verified: the same inside the rebuilt plug-in in Bitwig (needs the plug-in to be reloaded there).

### Waveform: time labels, fade in / fade out (branch `feature/fade-handles`, version 0.10.0)
- **Handles redesigned** (`gui/WaveformView.*` rewritten): the start and end line are grabbed in the middle and lower part of the display (an orange knob sits on each line at half height); the top quarter belongs to two new small squares, the **fade-in and fade-out handles**. The orange line is now the **envelope** of the played part: from the start line up to the fade-in square, along the top, down from the fade-out square to the end line (without fades it is the old vertical line). Faint vertical guide lines mark where start and end can be grabbed when the envelope is slanted.
- **Time displays:** the start and the end line show their time in the sample in seconds (small label at the bottom); a fade handle shows "fade 0.206 s" while the mouse is over it or drags it. (The author asked for the end handle only; the start handle got the same label for symmetry.)
- **Engine:** new parameters `FadeIn` and `FadeOut` (seconds, 0 - 10, default 0). The voice multiplies the sound by a linear envelope tied to the **sample's own time**: min(1, (position - regionStart) / fadeIn, (regionEnd - position) / fadeOut). So a reversed sound begins inside the fade-out part (what the waveform shows is what is heard, mirrored). Both fades together are shortened in proportion if they exceed the region; the duration of the sound, and so the exactness of play to end, is unchanged. Test: constant sample, fade in 100, fade out 200 samples: 0 at the start, 0.5 halfway, 1 in the middle, 0.5 halfway down, 0 at the end, and the reversed case.
- **Checked with real mouse input** (XTest on the Standalone window, no sample loaded, so the display covers a nominal 1 s): dragging the end line from the right edge to the middle gave 0.576 s; dragging the fade-in square at the top gave a fade of 0.206 s and the envelope followed. Snapshot with a cymbal, region 0.05 - 0.8, fades 0.03 s and 0.25 s: looks as intended.
- Factory presets regenerated (version 3, fades 0); manual and controls list updated.

### Step 1: pan per step, engine (branch `feature/step-pan`, version 0.11.0)
- New parameter per step (`Step01Pan` ... `Step32Pan`, -1 left, 0 centre, 1 right, default centre). The voice applies a **balance law** (`panGains`): the centre keeps the full level of both channels (so nothing changes for existing patterns), panning to one side only turns the other channel down (never louder); a mono output ignores the pan; MIDI notes play in the centre.

### The pluginval crash (4): what was found
- **Where it crashes:** with gdb, in pluginval's own VST3 run loop (`juce::RunLoop::Impl::registerEventHandler` lambda, `unordered_map::operator[]`), on the main thread while it dispatches the event of a file descriptor. At the crash the fault address is not a null pointer but a half-garbage address (`0x555556a67`, a truncated heap address) and the object registers hold heap fragments: the host calls a callback whose captured `RunLoop::Impl` object has already been freed (**use after free in pluginval, not in the plug-in**). Only the main thread, a sleeping test thread and pluginval's timeout thread exist at that moment, so it is not a race of two threads in our code. The plug-in's JUCE VST3 wrapper registers an event handler with the host's run loop in the constructor of every instance (`ScopedRunLoop` in `JuceVST3Component`, seen with gdb), like every JUCE plug-in.
- **Frequencies** (pluginval 1.0.4, Linux, virtual display, GUI tests skipped unless noted): 0.10.0 Release 1 of 20; this plug-in with 650 parameters 5 of 40 (no asynchronous update 5 of 40, so that is not the cause); **factory presets not deployed in the constructor 1 of 40; presets neither deployed nor read in the constructor (loaded when the first editor is created) 0 of 60**; with the GUI tests (editors are created, the presets are loaded then) 5 of 24; AdvancedAudioTemplate plug-in (one parameter) 0 of 30; TomicDrumSynth 0 of 20.
- **So the author's suspicion is right as far as the evidence goes:** the preset deployment and reading in the constructor makes the crash far more likely (12 % -> 0 of 60), and it comes back as soon as the same work is done at the first editor creation. The work takes only about 50 ms (34 ms deploy and 16 ms reading in a Debug build, measured with the new debug log), so it is not a long block; presumably it changes the timing in which pluginval deletes plug-in instances and messages of the plug-in are still pending (the crash is always at the end of the fuzz test or at the exit, and the rate rises with the number of parameters, i.e. the number of parameter notifications the plug-in sends). The exact mechanism inside pluginval's run loop was not found.
- **What was changed:** the factory presets are now deployed and the preset files read when the first **editor** is created (`ensurePresetsLoaded()`), not in the constructor: instances are created much more often than editors (scanning, tests), so this is also faster to load. `tools/run_pluginval.sh` keeps its tolerance for the host crash (see above) as a safety net.
- **Not done:** removing the cause completely; options if it matters: far fewer host-visible parameters (the step data as part of the saved state instead of 650 automatable parameters), or preset files that only contain what differs from the default.
- **Comparison with another of the author's plug-ins and the final build:** JadeSpectrogram2 (JUCE, AAT based) with the full pluginval run including the GUI tests: 0 of 30 crashes. The installed Release build 0.12.0: 8 of 8 full runs without a crash or warning (the Release build is faster, which seems to make the crash rarer; the Debug build with GUI tests still crashed in about one run of five before the script repeated it). The debug flag file `/tmp/dfd_debug.flag` that switches the diagnostic log on was removed again, so nothing is written to `/tmp` any more.


## Round 9: root cause of the pluginval crash (analysis only, no DFD code changed)

Question: is the intermittent SIGSEGV of pluginval a problem of our plugin or of pluginval?

Evidence:
- gdb (round 8): crash in pluginval's own VST3 host run loop (`RunLoop::Impl`, use-after-free in the fd-callback map), main thread, plugin code not on the stack.
- JUCE commit 04e167d646 (in 9.0.2) fixes exactly this host race (the Linux event loop copies callbacks per iteration, `~Impl` can run inside another fd's callback). pluginval 1.0.4 embeds JUCE 8.0.3 (without the fix).
- Decisive experiment: pluginval 2.0.0 built from source (JUCE 9.0.4, Release, `/home/bitzer/AudioDev/PluginvalAnalysis/pluginval`), same Debug plugin, `xvfb-run -a`, strictness 10:

| Plugin | pluginval 1.0.4 | pluginval 2.0.0 |
|---|---|---|
| DFD 0.12.0 Debug (with GUI tests), 30 runs | 3/30 crashed | 0/30 |

- Stress plugin (copy of AAT2, N float parameters, Y presets written and read in the constructor, env `STRESS_PARAMS` / `STRESS_PRESETS`, `--skip-gui-tests`, 20 runs per cell):

| Parameters | Presets | 1.0.4 crashes | 2.0.0 crashes |
|---|---|---|---|
| 1 | 0 | 0/20 | |
| 1 | 12 | 0/20 | |
| 1000 | 0 | 3/20 | |
| 1000 | 12 | 2/20 | |
| 1000 | 40 | 3/20 | 0/20 |
| 3000 | 40 | 8/20 | 0/20 |

Conclusions:
- It is a pluginval (host) bug, fixed upstream in JUCE 9.0.2. Not a mutex problem in our plugin: the race is inside the host's own run-loop bookkeeping.
- The crash rate scales with the number of parameters (0 at 1, ~12% at 1000, 40% at 3000), not with the number of presets (0 vs 12 vs 40 presets at 1000 parameters: no trend). Many parameters make instance creation/destruction slower and the plugin registers more work in the loop, which widens the race window; this is why DFD (~655 parameters) is affected and small plugins are not.
- A long-running constructor is not the trigger by itself (presets alone: no effect).
- No load was reduced for any of these results.

Consequences / open:
- `tools/run_pluginval.sh` should use pluginval >= 2.0.0 (JUCE 9.0.4) instead of tolerating the crash; the retry/"counted as passed" logic can then be removed (not done yet: user decides).
- Stress plugin is outside the repository: `/home/bitzer/AudioDev/PluginvalAnalysis/StressPlugin`.

## Round 10: parameter redesign, step 1: the patterns are data, not parameters (0.13.0)

Request: the pattern and the control values do not have to be automatable, so they need not be parameters; plain arrays saved as blobs in the presets will do; no compatibility with old presets needed.

What changed:
- `src/PatternData.*` (new, pure C++): 4 patterns x 32 steps x 5 values (on, mode, note, velocity, pan) and the 4 play switches, in lock-free atomics (GUI thread writes, audio thread reads). Saved as one blob (`toBytes` / `fromBytes`, format version 1, documented in the header: magic "DFDP", counts, play mask, little endian floats; about 2.6 kB). Invalid blobs (size, magic, version, counts) are refused; values are limited to their ranges.
- `src/StepParameters.*` became `src/StepValues.*`: only ranges, defaults and help of the 5 values (no ids, no parameter specs).
- The plugin state holds the blob as the property `PatternData` (base64) of the state tree, so presets (XML attribute), DAW projects and the preset handler need no new code. `commitPatternData()` writes it after every edit; a preset or DAW state load (`valueTreeRedirected`) reads it; a state without a valid blob keeps the current patterns and writes them back. `getStateInformation` stamps the blob into the copy of the state.
- The edit pattern (which pattern the grid shows) is not saved any more; it is plain GUI state of the `PatternSelector`.
- GUI: `StepGrid`, `StepColumn`, `StepStateButton`, `ValueStrip`, `PatternSelector` work on `PatternData` instead of parameter attachments (no gestures); the editor turns the Save button red when the `PatternData` property changes. The grid shows a loaded preset because the GUI timer compares `PatternData::getLoadCount()`.
- Parameters: from about 660 to 11 (base note, start, end, pattern length, step note value, sync, tempo, internal play, fade in/out, declick). pluginval: Debug, 3 runs, SUCCESS.
- Factory presets: `tools/make_factory_presets.py` writes the blob (python `struct`, same format), preset version 6; the files shrank from about 650 to 11 lines.

Checks:
